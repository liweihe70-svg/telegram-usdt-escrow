# 稳定性验收（本地模拟）

2026-10-13 新增10项稳定性测试，总计83项自动测试通过。测试使用独立内存或 `data/qa-stability-*` 数据目录，没有调用真实 Telegram、修改系统网络设置或连接钱包。

| 场景 | 验证结果 |
| --- | --- |
| 模拟短时断网 | 使用项目实际 Telegraf SDK 的轮询实现，第一次请求注入 FetchError；5秒后恢复，并继续用正确的更新偏移 |
| 限流与服务错误 | 注入429/503，按 SDK 重试规则恢复 |
| 凭据失效或轮询冲突 | 注入401/409，停止轮询，避免反复争抢实例 |
| 普通网络请求超时 | 超时后返回可重试错误，不返回原始错误地址；普通调用限制15秒，长轮询保留50秒服务等待并加15秒余量 |
| 停止时有网络请求 | 生命周期取消信号取消等待中的 API 请求；SDK 更新偏移同步也受此信号限制 |
| 慢后台任务 | 超过旧1.5秒等待时间时，停止仍等待任务结束，期间拒绝重新启动 |
| 旧启动探测延迟返回 | 旧探测不能停止已启动的新实例；重复停止只关闭一次 |
| 通知发送失败后数据库重开 | 重试时间及成功收据保留，只补发未成功收件人 |
| 重复启动恢复通知 | 同一订单尚未发送的 BOT_RESUMED 通知合并为一条，保留原记录 |
| 大量失败通知 | 50条失败通知进入延迟队列后，后续健康收件人仍能收到消息 |
| 结算子进程异常退出 | 子进程在模拟广播提交后直接退出，未关闭数据库；重开后沿用原出款ID与哈希，完成结算后仅一次出款记账 |
| 高频重复确认 | 12笔商品/P2P订单，共384次重复确认请求，100轮后台循环；每单一笔出款、一次出款记账，账本总和为0 |

## 修复内容

1. 停止机器人时显示「正在停止 / Stopping」，取消其网络等待并等待后台任务排空，不再在1.5秒后允许新工作器启动。
2. 启动失败的清理只作用于该次启动创建的机器人，旧探测延迟返回不干扰新实例。
3. 增加未发送启动通知的数据库唯一约束，并将旧版本的多余待发启动通知标记结束，避免恢复时堆积相同通知；没有删除订单或账目。
4. 为 Telegram API 请求加超时和生命周期取消，覆盖探测、轮询、后台通知及私聊/群消息回复；附件内容下载仍有其原有30秒限制。
5. 更正争议入口帮助文字，说明文字、图片和文件证据均可提交。

## 仍待真实验收

这轮验证包含模拟故障、真实 SDK 执行路径和本地子进程恢复，不等于真实 Telegram 网络故障、机器突然断电或数天连续运行已经验证。真实双账号互相确认、通知接收、群权限及附件上传仍留到最后。

Telegram 发送消息与数据库收据不是同一个事务：若服务端已接受消息而本地尚未保存收据就异常退出，恢复后仍可能重复一条消息。已提交结算、出款身份和账本的数据库约束另行验证，不能把消息去重表述为严格的「只发送一次」。本项目仍仅使用模拟资金。
