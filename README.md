- 交易概览：托管余额、已完成订单、待处理争议、费用与最近操作。

- 争议处理：查看约定和操作记录，填写买卖双方分账与裁决理由，执行模拟结算。
- 出款记录与资金账本：查看模拟交易哈希、收款方、出款状态、异常入金负债和账户平衡。
- 机器人配置：在本机填写测试 Token、管理员 ID、品牌及费率，保存后主动启动或停止长轮询。页面不回传已保存 Token。

点击“快速演练”创建一笔100 USDT商品订单，然后在详情中依次模拟双方确认、入金、交付和买家放款。机器人运行时后台自动处理模拟结算；未运行时可手动完成模拟结算。退款与争议也可从已入金订单操作。所有记录持久化保存。

从面板启动的机器人与面板共用 `data/local-demo`，不要同时使用相同 Token 启动独立 `npm run bot`。面板操作代表本机模拟参与方，不是生产管理员权限系统。只允许本机访问；变更请求校验控制会话及来源，禁止将此服务公开到互联网。

## Telegram 内测启动

在 BotFather 创建测试机器人，然后在本机填写配置。不要把 Token 发到聊天中。

```powershell
# 仅在不存在 .env 时复制，保留已有配置。
if (-not (Test-Path -LiteralPath .env)) { Copy-Item -LiteralPath .env.example -Destination .env }
notepad .env
npm run bot
```

填写 `TELEGRAM_BOT_TOKEN` 和自己的 `ADMIN_TELEGRAM_IDS`（数字 ID，多个用逗号分隔）。机器人启动后可发送 `/id` 查看本人 ID；如需补充管理员配置，停止机器人、修改 .env，再重新启动。未配置管理员时，所有测试注资和仲裁权限拒绝。

机器人使用长轮询，用户名由 getMe 获取，不通过配置猜测。资金仍为模拟。它不启动开发 HTTP API，默认数据库独立位于 `data/telegram-demo`；不要让两个进程同时打开相同 PGlite 数据目录。不要用真实业务 Token 测试，启动轮询会影响该 Token 原来的接收方式。

### 交互路径

### 中英文语言选项

首页点击 **🌐 中文 / English**，或发送 `/language` 选择语言。`/language en` 切换英文，`/language zh` 切回中文。默认中文，偏好按用户保存在本地数据库，机器人重启后保留；不同用户可以选择不同语言。

所选语言用于菜单、创建向导、订单状态、查询、通知、说明、错误提示及管理员演练/争议/仲裁。交易约定、证据和裁决理由保留用户输入原文，品牌名称作为配置原文保留。语言切换不会改变金额、身份或正在填写的草稿。旧消息不自动改写，刷新订单后显示所选语言。

### 双方交易步骤

1. 双方分别私聊机器人，发送 `/start` 和 `/id`。
2. 一方点击创建担保交易，选择类型、角色，填写对方数字 ID、本金、交付约定。
3. 核对费用，点击创建订单，把订单卡里的邀请链接转发给指定对方。
4. 双方分别确认交易条款。邀请链接不授予身份，其他用户不能查看订单。
5. 已配置的测试管理员私聊发送 `/simulate_deposit 订单完整编号`，注入足额模拟入金。普通用户无法运行。
6. 商品由卖家声明交付、买家验收；P2P 由买家声明法币付款、卖家核实到账。
7. 放款需再次确认，后台模拟结算 worker 自动完成模拟出款，通知双方。

首页包含我的交易、收费规则、使用说明、担保介绍及本人 ID。`/cancel` 取消尚未创建的填写草稿；订单取消通过订单卡操作。争议及退款遵循数据库权限；管理员可以通过 `/admin` 查看争议和提交模拟仲裁。详细演练步骤见 [完整模拟版使用说明](docs/simulation-guide.md)。

已配置的管理员发送 `/demo`，选择商品或USDT买卖、自己的角色、金额和约定，机器人自动生成系统模拟对方。专用演练按钮仅限创建者管理员，只能作用于这类演练订单，不能代替普通订单里的对方操作。双方确认情况显示在订单卡，自己已确认后隐藏重复确认按钮。

`/dispute 完整订单编号 理由` 准备争议申请，核对后二次确认；`/evidence 完整订单编号 说明` 追加文字证据；`/evidences 完整订单编号` 分页查看记录。每位参与方最多10条、每条最多1000字，管理员可阅读但不能冒充参与方提交。

`/disputes` 列出待处理争议，`/arbitrate 完整订单编号 买家金额 卖家金额 裁决理由` 准备方案。仅管理员可用；双方分配总额必须等于可分配资金，确认后进入模拟结算。方案10分钟失效，可取消，替换或重复确认不会重复出款。

补充的私聊命令：`/instructions`、`/rules`、`/whatisescrow` 返回说明；`/buyer`、`/seller` 返回角色指南；`/video` 当前提供文字演练并说明尚无视频。`/terms 完整订单编号`、`/description 完整订单编号` 查询已锁定约定；`/balance 完整订单编号` 查询模拟托管与异常款账本余额，仅交易双方可访问。`/qr` 明确尚未启用收款二维码。帮助和查询不改变正在填写的草稿或订单资金。

`/menu` 打开快捷菜单；订单卡提供条款、模拟余额和出入金记录按钮。`/blockchain 完整订单编号` 展示本机模拟入金和出款记录，明确 simtx 哈希不是真实链上交易；不提供伪区块浏览器链接。实时汇率及第三方链接验证尚未接入。

### 接入边界

- 47项自动测试使用离线合成 update，核验 from.id 身份、按钮回调、权限、退款、争议、账本、结算恢复和中英文语言偏好。实际桌面Telegram还验证了单账号P2P完成、文字证据、仲裁及通知，以及中英文切换和查询；没有验证手机端或两个真实账号的成功配对。
- 向导草稿保存在数据库，一小时失效。Telegram update 先持久化领取，重复文本不会推进两次；中断请求状态不确定时不盲目重放，用户需刷新订单核对或重新填写。
- 消息仅发送到用户自己私聊登记的 chat ID。通知逐收件人记录，失败重试；发送成功但回执落库前崩溃仍可能重复通知，订单与出款去重独立生效。
- 默认模拟收费为最低5 USDT或本金5%中较高者，由入金方额外承担；这是可配置演示政策，不代表已经确定真实收费。
- 已实现手动建群后的订单绑定；自动建群、真实链入金、真实出款及生产后台登录界面尚未实现。本机模拟控制面板已实现。

## 费用假设

面板和机器人按配置计算费用（默认最低5 USDT或本金5%中较高者），旧模拟 API 显式传入 fee。付款方支付本金加手续费：100 USDT 本金＋5 USDT 费用＝105 USDT 入金；普通放款支付100，平台收入5；双方退款退105；仲裁暂不收费，双方分配合计105。全部金额为最多六位小数的字符串，内部使用整数最小单位。

## API

所有 POST 为 JSON，须先 GET `/api/session` 获取 controlKey，再通过 `x-control-key` 请求头提交。身份字段是本机模拟输入，不是身份认证，禁止公开此开发 API。

| 路径 | 请求 |
| --- | --- |
| POST /orders | kind=PRODUCT或P2P、buyerId、sellerId、principal、fee、buyerAddress、sellerAddress、description |
| GET /orders/:id | 订单状态 |
| POST /orders/:id/accept | actor、version=1 |
| POST /orders/:id/deposit | network=SIMULATED_TRON、token=SIM_USDT、txHash=simtx:唯一值、eventIndex、amount、confirmed=true、success=true、to=订单收款地址 |
| POST /orders/:id/action | actor、action |
| POST /orders/:id/arbitrate | buyerAmount、sellerAmount、reason，本机面板内部管理员 |
| GET /orders/:id/payouts | 出款任务 |
| POST /orders/:id/broadcast | {}，仅生成模拟广播结果 |
| POST /orders/:id/confirm | payoutId、txHash，模拟已确认链上回执 |

action 可为 DECLARE、RELEASE、REQUEST_REFUND、REJECT_REFUND、AGREE_REFUND、DISPUTE、CLOSE。

PRODUCT：卖家 DECLARE，买家 RELEASE。P2P：买家 DECLARE（声明法币付款），卖家 RELEASE。退款必须另一方 AGREE_REFUND。

## 已实现

- 双方确认同一版本后锁定交易；订单创建后本版本不支持修改条款。
- 订单行锁、唯一结算任务、链上事件与记账幂等。
- 足额已确认模拟入金记入订单；少付、多付、重复额外入金及迟到入金分别记录为异常负债，不自动结算。
- 争议暂停普通结算；Telegram 管理员白名单默认空。本机面板使用不能由 Telegram 用户 ID 对应的内部管理员来进行模拟仲裁。
- 仲裁分账金额守恒，所有出款确认后才结束订单。
- 签名字段为模拟标记，持久化模拟交易身份后可在重启时恢复。
- 数据库提交时检查账本平衡，历史账目及审计记录禁止修改。
- 事务内写入 outbox 通知事件，避免状态成功而通知事件丢失。

## 后续接入范围与验收边界

本版本没有 Telegram webhook、自动建群、真实 TRC20 日志监听、真实签名、能量管理、生产后台登录界面、异常款人工退款接口或对外部署。阶段超时任务、文字与文件证据、群绑定、长轮询和通知任务消费者已实现；主要私聊流程已完成桌面单账号联调。群及两个真实账号流程仍待验收。尚未验证真实 PostgreSQL 多进程竞争；嵌入数据库中的并发测试不等同于生产分布式验证。

后续顺序：真实 Telegram 内测及群绑定 → 真实 PostgreSQL 迁移及多连接竞争验证 → 测试链转账事件监听 → 独立签名服务与对账 → 生产管理员身份认证 → 限额内测。

真实链监听必须根据允许的合约、收款地址、成功的 Transfer 事件及固化确认入账，不能信任 API 客户端传入 confirmed=true。签名服务必须独立核对订单分配方案；实际重发、过期交易替换与未知回执恢复需要专项测试。
